# 采购询比价：功能、验收与部署

本轮完成 P0、P1，沿用 React、Gin、GORM、MySQL 和既有账号、审核、操作员权限、存储配额、备份恢复能力。询价和主动采购共用一份采购项目；扩大邀请范围不复制项目。没有引入消息队列、WebSocket、AI、支付或合同组件。本轮只在本机和隔离数据库验收，未部署生产、未向生产插入测试资料，未更新原生 App 安装包。

## 使用入口

网站顶部统一为一个“采购中心”：未登录进入公开需求大厅，已登录进入我的询价与需求。采购页面采用厂商工作台同款深蓝侧栏、白色顶栏和卡片布局，侧栏依次为“我的询价与需求、发布采购需求、采购需求大厅、消息通知、采购商资料”。厂商收到询价、报价、历史、洽谈和订阅均在厂商工作台的商机中心完成；普通采购账号引导使用原账号入驻。桌面侧栏支持独立收起，900 像素及以下改为抽屉导航，支持遮罩、Escape、键盘焦点循环和栏目切换关闭。见[采购中心界面调整及验收](PROCUREMENT_WORKSPACE.md)及[隔离演示说明](PROCUREMENT_DEMO.md)。

| 入口 | 功能 |
| --- | --- |
| 产品详情“立即询价” | 带入公开产品、型号参数、所属厂商，登录后继续填写，默认定向询价 |
| `/buyer` | 我的询价和需求、状态过滤、报价比较、意向供应商、独立洽谈 |
| `/buyer/new` | 多产品需求、云端草稿、联系人、交货地区、截止时间、附件和邀请方式 |
| `/buyer/profile` | 在原账号上登记或修改采购商资料，厂商可同时采购；采购账号也可使用原账号入驻厂商 |
| `/procurement` | 经审核的有效公开摘要，按展馆、产品类别、关键词、交货地区和截止状态筛选 |
| `/merchant/opportunities` | 收到的询价与商机、逐项报价、修订撤回、报价历史和独立洽谈 |
| `/merchant/opportunities/settings` | 厂商商机通知订阅；厂商通知为 `/merchant/opportunities/notifications`，采购消息为 `/buyer/notifications` |
| `/admin/procurement` | 项目查询、审核、匹配原因、补充邀请、异常处理、账号限制及统计 |
| 企业资料编辑“供货产品类别与地区” | 多选产品类别、供货省份；随企业资料版本一起审核 |

采购登记只必填联系人和已验证手机号，采购单位和所在地区选填。复用手机号注册、密码登录、公司账号登录及绑定验证；新增手机号验证码登录，只登录已有且已验证手机号的业务账号，不自动注册、不自动创建厂商、不允许管理员使用。开发短信模式显示动态验证码，正式阿里云模式不返回验证码。业务账号共用 `zqzt.merchant` 会话槽位，平台管理员仍使用独立会话。`/auth/me` 增量返回 `buyer_registered` 和 `capabilities`，保留旧字段。原 `/buyer/opportunities/*` 兼容跳转到厂商工作台，保留查询参数及锚点。

管理员或具有 `procurement.review`（审核采购需求）权限的操作员，在管理后台“采购中心 → 需求审核”（`/admin/procurement/reviews`）打开待审核记录，点击“查看资料并审核”，在项目页审核通过或填写原因驳回。普通采购商和厂商不能自行审核。首次定向产品询价直接送达，发布采购需求或扩大邀请范围需审核。

表单按产品、交付联系、附件和邀请范围分组，一个项目最多 30 项。先保存草稿，再上传附件。草稿会保留邀请方式及指定厂商。源产品加载完成后才开放询价编辑，避免异步资料覆盖用户输入。界面延续蓝白样式，中英文切换；电脑比较表固定产品列，手机按产品切换厂商报价卡片。

## 生命周期和版本

1. 草稿可保存及继续编辑，每次保存创建新需求版本，旧草稿和旧待审请求标记为已替代。
2. 首次产品询价立即送达所属厂商；即使表单选择扩大范围，也先定向送达并在同一发布版本申请扩散审核。公开、同类匹配及指定邀请需求均先审核；已有定向询价扩大邀请范围时，在同一项目的已发布版本上申请扩散审核。
3. 修改已发布内容生成新版本，审核期间旧发布版本继续有效。通过后报价历史保留，旧报价标记“对应旧需求，需重新报价”。仅扩大邀请范围不会改变需求版本或使报价失效。
4. 截止时间按服务端 UTC 时间判断，界面显示浏览器本地时间。截止后禁止提交、修订和撤回报价，但可继续洽谈；延期按新版本审核处理。
5. 完成、关闭、取消均保留历史，停止新报价和发消息。完成是采购商结束本次询比价，不表示平台确认交易成交。

每份报价包含逐项供货状态、人民币单价、起订量、交货天数，以及整份报价的税费、运费、有效期和备注。至少一项有效报价才能提交，未报价和不供货均有明确状态。保存草稿、修订和提交分别创建不可覆盖的报价版本；采购商看不到厂商未提交的草稿。

数量使用 `DECIMAL(18,3)`，单价使用 `DECIMAL(18,4)`，运费使用 `DECIMAL(18,2)`，API 均传十进制字符串。使用需求原单位，不自动换算。仅当前版本、有效、完整覆盖、满足起订量且含税并已知运费的报价才显示可比较到货总价；部分报价、税费或运费待议均不计算具有误导性的整包总价。采购商可以选择多家意向供应商，不按最低价自动成交。

## 匹配、权限与私密资料

匹配先限定同一开放展馆和审核公开的厂商，再读取审核通过的供货产品类别和公开产品分类，按分类精确程度、主营产品及关键词命中、供货地区排序。经营分类和产品分类属于不同体系，不直接比较 ID。厂商只有经营分类、尚无产品供货类别时，应先补齐产品供货类别；不会据经营分类 ID 猜测供货能力。

明确不覆盖交货地区的厂商排除；没有填写范围时标记“待确认”，不使用注册地址推断全国供货。自动首批最多 20 家，可补邀；每次最多 20 家，单项目累计推送最多 100 家，项目和厂商唯一去重。符合分类、地区条件的公开厂商可主动加入公开需求，主动参与不占推送名额。指定项目仅指定厂商参与。自己的账号不能向自己的厂商询价或自行报价。

公共接口使用独立摘要结构，只含项目及产品名称、类别、数量单位、交货地区、截止时间等。项目采购商可比较全部已提交报价；厂商接口只查询本厂商的报价及独立会话，不能枚举竞争对手报价、会话附件或参与名单。采购商必须明确确认意向后，该厂商才获得项目联系人电话。其他厂商继续通过站内消息沟通。

操作员新增权限：`procurement.read`、`procurement.review`、`procurement.quote`、`procurement.match`、`procurement.manage`、`procurement.stats`。授予任一采购权限时允许进入采购查询；查看报价及报价、消息附件仍额外检查 `procurement.quote`。后台异常处理必须填写原因，关键操作写入既有日志，不将报价正文及电话复制到日志或访问统计。

创建、提交、邀请、报价和其他业务写接口需要 `Idempotency-Key`；同账号同键同请求重放原结果，换内容重用返回 409。前端在网络结果不确定时保留重试键。事务按账号、项目加锁，状态编辑检查 `version`，审核检查精确需求版本，避免旧审核和关闭后并发提交。文件上传独立受配额、大小及频率限制，尚未绑定的上传可在 24 小时后回收。

业务 API `Cache-Control: no-store`，采购私有接口及附件附加 `X-Robots-Tag: noindex`。采购网页使用 `noindex,follow`，不进入既有厂商、产品站点地图。权限不依赖 User-Agent。

## 私有附件与通知

附件支持 JPG、PNG、WebP、PDF、DOCX、XLSX。每个需求版本、报价版本或消息最多 10 个，单个最多 20 MiB；不支持压缩包、CAD 或宏文件。验证扩展名、实际图片类型、像素尺寸、PDF 页信息；Office 检查 ZIP 内部文档根、内容类型、宏、ActiveX、重复或越界路径，最多 2,000 项、每项解压 20 MiB、总解压 100 MiB。

附件使用独立 `procurement/` 对象路径，复用现有容量预约及账号配额，记录在 `procurement_attachments`，不生成公开媒体 ID、不加宣传水印。下载和预览经业务鉴权代理读取，不返回公开 OSS 地址；Office 只下载，图片及 PDF 可预览。OSS 沿用官方 SDK 的私有、禁止覆盖上传。反向代理不得将 `MEDIA_DIR` 或 `procurement/` 目录配置为可直接下载的静态目录。

对象清单、存储迁移、配额和备份包含采购附件；恢复时检查对象存在及项目、版本、消息作用域是否完整。复用附件到新版本时只增加引用记录，不复制对象字节。已绑定版本保留历史；进程内分钟任务清理从未绑定且超过 24 小时的上传，遵守维护和暂停写入开关。

站内通知与业务事务同时落库，覆盖询价、邀请、报价、回复、意向、审核和结束。商机订阅有即时、每日汇总、关闭三种，默认即时；每日最多 20 条即时商机提醒，超额合并到北京时间 18:00 的每日汇总（当天该时刻已过则次日）。通知到达时间持久化，重启不丢失；同项目、厂商、需求版本的邀请提醒去重。定向询价、报价和回复不受关闭商机订阅影响。可见页面每 30 秒查询未读数。

通知列表新增可选 `scope=buyer|supplier`，标记已读请求新增同名可选字段。采购与厂商工作台分别按身份查询、计数和标记已读；未传范围时维持原全部消息行为。按当前账号及项目采购商归属筛选，无项目商机汇总归厂商侧。不复制通知、不新增迁移。

只预留独立 `ProcurementSMSNotifier` 接口，首版不发商机短信，也不借用验证码模板。

## 数据和接口

迁移文件为 `server/migrations/021_procurement.sql`。新增 14 张业务表，包含采购商资料、项目、需求版本和明细、审核、参与邀请、报价及版本明细、独立消息、私有附件、事件幂等、通知及订阅。只增量建表，不重写现有业务数据；企业供货配置存在既有 JSON 资料版本内，不给历史企业虚构全国供货范围。

主要 API 位于 `/api/v1/procurement`：`profile`、`projects`、`draft`、`submit`、`expand`、`state`、`matches`、`invite`、`join`、`quotes`、`quote-withdraw`、`participants/{vendor}/state`、`messages/{vendor}`、`attachments`、`notifications`、`preferences`。公开摘要为 `/api/v1/public/procurements`，厂商选择为 `/api/v1/public/procurement-vendors`，后台为 `/api/v1/admin/procurement`。完整契约见 [OpenAPI](openapi.json)，维护脚本为 `scripts/update-procurement-openapi.mjs`。

## 部署和回滚步骤

1. 先在预发布环境备份现有数据库和完整对象，保留配置加密密钥、运维控制目录、存储配置和上一版后端及网页文件。验证备份可在隔离环境恢复；不要只备份公开媒体。
2. 维护窗口暂停写入，同步发布新后端和完整 `web/dist`。后端启动执行嵌入迁移，确认 `schema_migrations` 到 21、新表存在、原有资料数量不变。迁移采用 `CREATE TABLE IF NOT EXISTS`，可重入；不要手动删除迁移版本来跳过失败检查。
3. 首次生产发布可设置 `PROCUREMENT_ENABLED=false`。该开关阻止新业务写入、上传及公开大厅，公共询价入口隐藏，已授权历史记录仍可读取；关闭不会删除数据或阻止 Schema21 迁移。设置 `true` 并重启后启用。默认值为 `true`，生产应显式配置。
4. 延续现有短信、对象存储、容量及配额配置，无额外队列配置。若反向代理限制请求体，为采购上传允许至少 21 MiB，同时保留现有大文件接口配置；CORS 需允许 `Authorization`、`Content-Type`、`Idempotency-Key`。验证私有路径不能绕过应用直读；OSS 必须保持私有 ACL。
5. 为审核人员分配采购权限。在预发布账号下验收审核、匹配、私密报价、意向电话、附件下载及移动布局。检查历史厂商补充供货产品类别、地区后需审核才影响匹配，不能误用未审资料。
6. 用新版备份验证包含 `procurement/` 对象和全部采购表，恢复上限已从 Schema20 提升为 Schema21，仍接受原有支持的 Schema10–20 备份。旧版本服务不能恢复 Schema21 备份，不要用旧版恢复入口处理新备份。
7. 应急先设 `PROCUREMENT_ENABLED=false` 并重启。优先保留新版后端及 Schema21，只隐藏新业务；如需完整回退旧程序，应在维护窗口保全新增采购数据库和对象，再使用上线前匹配的数据库、对象及程序快照成套恢复。不要在已产生新采购记录后直接删表或仅恢复旧 SQL，以免丢失联系、报价和私有附件。

启用后观察审核积压、错误日志、配额与商机通知数量。上线操作、真实短信发送、AI、CRM、收费增值、支付合同及原生 App 界面均不属于本轮交付。
